# 广东城际接入可行性调查

调查日期：2026-09-29（America/New_York）。首轮接口实测约为 18:33–18:35 UTC；随后约 18:42–18:45 UTC 深入验证正晚点，均为北京时间 2026-09-30 凌晨。计划时刻查询的服务日期为 2026-09-29。

## 结论

广东城际值得进入接入验证阶段。已经从 12306 官方域名取得一趟广东城际列车的完整逐站计划时刻，证明存在可机器读取的计划数据。尚未验证覆盖广东城际的可靠实时到发预测，不能据此承诺实时 provider 已经可用。

推荐先验证计划时刻覆盖与维护方式，再独立评估正晚点/车站大屏。广东城际官方“城际出行助手”也是优先候选来源，不能只围绕 12306 调查。

本次未发现面向公众开发者、具有明确接口契约与再发布条件的 12306 / 广东城际实时开放 API 文档，也未找到官方 GTFS-RT 下载地址。这是本次检索范围内的结果，不是不存在合作接口的证明。公开网页可调用的接口，不等于已获得长期稳定性或数据再发布承诺。

## 已实测的 12306 接口

以下是旅客查询页面背后的接口，不是已确认的开发者开放平台。请求未携带个人账户、登录 Cookie 或验证码凭据；未进行批量采集或压力测试。

### 1. 车次检索：成功

```text
GET https://search.12306.cn/search/v1/train/search?keyword=C4731&date=20260929
```

响应摘录：

```json
{
  "date": "20260929",
  "from_station": "广州莲花山",
  "station_train_code": "C4731",
  "to_station": "惠州  北",
  "total_num": "21",
  "train_no": "6t000C47310E"
}
```

公开显示的车次号和内部 `train_no` 是不同字段。当前样本不证明其跨日期或跨运行图稳定性。

### 2. 逐站时刻：成功

```text
GET https://kyfw.12306.cn/otn/queryTrainInfo/query?leftTicketDTO.train_no=6t000C47310E&leftTicketDTO.train_date=2026-09-29&rand_code=
```

返回 `status: true`、`httpstatus: 200` 和 21 条停站记录。例如：

| 站序 | 车站 | 到达 | 出发 |
| --- | --- | --- | --- |
| 01 | 广州莲花山 | `----` | 06:25 |
| 03 | 东莞西 | 06:38 | 06:40 |
| 05 | 西平西 | 06:53 | 06:55 |
| 08 | 松山湖北 | 07:12 | 07:14 |
| 21 | 惠州北 | 08:35 | 08:35（原始字段） |

可用字段包括 `station_no`、`station_name`、`station_train_code`、`arrive_time`、`start_time`、`arrive_day_diff`；首条记录还提供始发和终到站名称。

这些是计划时刻，没有证据说明是实际到发或实时预测。时间只发布到分钟。终点记录也有 `start_time`，不能不加解释地把它展示为终点发车事件；始发站 `----` 也不能转成午夜。样本中的站名“惠州  北”包含内部空格，站名匹配需要别名/规范化策略，优先使用已核验的站码。

官方页面：[列车时刻查询](https://kyfw.12306.cn/otn/queryTrainInfo/init)。本次成功读取不代表该接口始终免验证。

### 3. 列车开行状态：成功，但不是 ETA

从[官方列车状态页](https://www.12306.cn/index/view/infos/train-query-status.html)引用的[公开脚本](https://www.12306.cn/index/script/dist/train-query-status/main_v60011.js)确认：

```text
POST https://www.12306.cn/index/otn/slide/checkSlide
POST https://www.12306.cn/index/otn/index12306/queryTrainStatus
```

本次验证开关返回 `ifOpenNewXXCXSlide: "N"`。按无滑块分支发送：

```text
trainDate=20260929&from=EGQ&to=HUA&station_train_code=C4731
```

业务响应为：

```json
{"result":"Y","data":"列车正常开行。"}
```

这证明能查询该车次的开行状态；不能将“正常开行”解释为“准点”，也不能由此产生 `delaySeconds: 0` 或实时 ETA。网页代码支持开启验证后提交滑块参数，因此本次关闭验证不构成长期自动访问保证。

### 4. 站码：已在官方目录确认

[官方站名脚本](https://www.12306.cn/index/script/core/common/station_name_new_v10118.js)包含：番禺 `PYA`、花都 `HAA`、佛山西 `FOQ`、广州长隆 `GCA`、西平西 `EGQ`、惠州北 `HUA`。目录覆盖车站不等于实时信息覆盖这些车站。

### 5. 浏览器直连：当前样本不支持

对逐站时刻接口添加 `Origin: http://localhost:5173` 后，仍返回 HTTP 200，但没有 `Access-Control-Allow-Origin`。车次检索普通请求也未返回该响应头。

因此，命令行成功不能作为 UMF 前端可直接跨域读取的证据。预计需要服务端采集/缓存或同源代理；生产来源仍需单独验证。未取得官方调用频率、缓存时效或 SLA。

## onTimeOrLate 深入验证

已保存[原始业务响应与车次候选快照](research/12306-ontime-probe-2026-09-29.json)。采集时间不代表上游数据生成时间。以下均为少量匿名请求，不涉及绕过验证。

### 请求流程与参数

1. `POST https://kyfw.12306.cn/otn/zwdch/queryCC`，表单参数 `train_station_code=EGQ`，用于车次输入候选。
2. `POST https://kyfw.12306.cn/otn/slide/checkSlide`，空表单，本次返回 `ifOpenNewXXCXSlide: "N"`。
3. `POST https://kyfw.12306.cn/otn/zwdch/query`，发送表单：

| 字段 | 含义/样例 |
| --- | --- |
| `cxlx` | `0` 到达，`1` 出发，来自页面按钮值 |
| `cz` | 中文车站名，例如 `西平西`；不是车站电报码 |
| `cc` | 展示车次，例如 `C4731`；不是内部 `train_no` |
| `czEn` | `encodeURI(cz).replace(/%/g, "-")`，西平西为 `-E8-A5-BF-E5-B9-B3-E8-A5-BF` |
| `randCode` | 本次空值；页面没有对应输入框，但脚本仍读取该字段 |

开启滑块分支时另有 `slideParam` 和 `if_check_slide_passcode_token`。当前开关关闭，不能据此假定以后都无需验证。脚本将查询按钮禁用 5 秒，这是页面节流行为，不是公开 API 配额或允许请求速率。业务请求没有日期参数，因此不能借它查询任意历史日期。

### 预计到发对照：K511 / 萍乡

当前为北京时间约 02:44，所查 2026-09-29 始发的 K511 计划在次日 04:58 到达萍乡、05:04 出发，落在未来三小时范围内。正晚点实际返回：

```json
{"result":"Y","flag":false,"message":"预计K511次列车，萍乡站到达时间为05:00"}
```

出发分支返回：

```json
{"result":"Y","flag":false,"message":"预计K511次列车，萍乡站出发时间为05:02"}
```

这是预计时间语义的直接证据，与计划时间也不同；尚未通过长时间观察确认更新频率或与现场实际的一致性。两条响应分别发出，不是同一原子快照。到达和出发相对计划的差值不同，不能用某站到达的差值统一平移整趟列车或所有事件。

特别注意：带有效预计时间的响应仍是 `flag: false`，并且时间在 `message`，不是 `data.data`。官方脚本在 `flag` 真时显示 `data`，否则将 `message` 弹窗展示。因此 `flag` 不能直接充当“有无预测”的判据，也不能把所有 `message` 都当作错误。当前仅核验了这些样本，不能猜测所有状态码和文本变体。

### 对 UMF 的具体影响

- 此接口按“车站 + 车次 + 到达/出发”查询，不是一次返回全站实时到发的 feed。需要先有可靠的当天计划班次集合，再为所需事件查询预测。
- 解码器必须识别严格的预计到达/出发文本，核对返回的车站、车次、事件种类。未知格式保留为未识别结果；“暂无”“失败”不代表无车、停运或准点。
- 响应只有 `HH:mm`，无服务日、源时间戳或显式晚点秒数。需结合当天计划与查询窗口消解日期；时间应为分钟精度 estimate，不能当作精确实测到发。跨午夜尤其需要明确策略。
- 正晚点接口的跨域实测也没有 `Access-Control-Allow-Origin`。当前共享 `HttpRequest`/resolver 仅发 GET；直接接源还需扩展 POST 表单能力与缓存键，或由服务端适配为统一读取接口。仅新增 JSON codec 不足以接通。
- 无源生成时间意味着不能用请求时间宣称数据刚更新。应独立记录采集时间、未知源时效和失败降级。
- 当前可以确认“12306 存在可读取的预计到发接口”。下一项决定性验证是广东城际运营时段、未来三小时内的实际车次；在该项通过前，广东城际实时覆盖仍未确立。

## 与当前 UMF 架构的匹配

当前仓库已有计划时刻 provider：见 [NBRT.md](NBRT.md)、[PROPRIETARY_HTTP.md](PROPRIETARY_HTTP.md)、`src/providers/registry.ts` 和 `src/domain/strict-time.ts`。

- 可新增独立 provider（建议 ID `gd-intercity`），覆盖多城市。地理范围不是 provider 必须按城市拆分的理由；也不能把所有广东省 C 字头列车都纳入广东城际。
- 若采用 JSON 接口，可沿用 `proprietary-http` 传输与 adapter 注册机制，但需要广东城际的数据规范化、线路归属与业务策略，不能只添加一份 manifest。
- 第一阶段配置 `predictions.kind: "none"`，按实际来源声明 schedule。循环更新计划表仍然是计划表；没有源生成时间时 `feedTimestamp` 应为空。
- 分钟计划时刻使用 `published-minute`；没有可靠预测时不计算晚点、不补造秒级精度。
- 先确认每日列车集合完整性，再声明 `coverage: "full-day"`。单趟 21 站成功不足以证明任何一个车站的全天班次齐全；按起终点查询也可能漏掉短线和跨线服务。
- 每趟停站序列可支持 trip path，但需核验服务日期、车次变号、内部 ID、跨日偏移和快慢车差异。用“provider + 服务日 + 内部车次号”可作为待验证的候选身份方案，不能预先承诺跨运行图稳定。
- 不能套用线路终点作为所有列车目的地，或认为快车停靠沿线所有车站。线路拓扑与每趟列车停站模式需要分别建模。

## 接入前的最小验证

1. 在可访问网络中读取官方助手，确认站点列表、逐站时刻和车站班次查询是否能正常匿名使用，记录字段含义与访问条件。
2. 以番禺、西平西、花都、佛山西等候选站为样本，核对双向、快慢车、短线、跨线与节假日加开；整理明确的运营方范围。
3. 在运营时段比较同一车次的计划、正晚点/大屏与实际变化，区分计划、预测、实际、开行状态、检票状态，测量数据更新时间。
4. 验证跨日、运行图更新和请求失败行为；确认可接受的调用/缓存/再发布方式。若存在验证或拒绝访问，按官方正常流程处理，不把绕过验证作为接入前提。
5. 有稳定计划数据即可建设 schedule-only 版本；实时模块仅在覆盖、新鲜度与语义均有证据后启用。当前仍属于 feasibility spike，尚未实现或发布 provider。
